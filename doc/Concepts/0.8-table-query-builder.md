# Concept: Table classes with query builder (0.8)

| | |
|---|---|
| Status | draft |
| Target | version 0.8 |
| Date | 2026-10-30 |
| Modules | PDO (`Table`, `Table\Reader`, `Table\Writer`), OSQL |

## Summary

Tables get **one** entry to the query builder: `query()`. What it offers depends on the kind of access –
a `Table\Reader` offers reading queries only, a `Table\Writer` writing queries only, a `Table` both, with
cache handling. The queries know the table: prefixed name, declared columns, keys, entity class,
JSON/DateTime columns, write rules and cache. Besides, the OSQL client accepts tables as source, and
`Table::readOnly()` hands out a table without any writing method.

```php
$orders->getAll( ['status' => 0] );                                    // table methods: simple, frequent cases

$orders->query()->select()->where( 'status', [0, 1] )->or( 'total', 1000, '>' )->page( 2, 20 )->all();
$orders->query()->update()->set( 'status', 2 )->where( Group::or( … ) )->execute();

$users->query()->select()->fields( 'username' )->join( $userGroups, 'ug' )->where( 'ug.groupId', [1, 2] )->column();

$client->select( $orders, 'o' )->join( $customers, 'c', 'o.customerId', 'c.customerId' )->…;   // client with tables as source

$reports	= $orders->readOnly();                                      // reading only, incl. query()->select()
```

## Motivation

Since 0.7.3, the database abstraction layer (PDO) and the query builder (OSQL) work on the same
connection and can be mixed – but they know nothing of each other:

| A table class knows | The query builder today |
|---|---|
| name **with prefix** | no prefixes – `'shop_orders'` has to be put together by hand |
| declared columns, primary key, indices | checks syntax only – a typo fails in the database |
| entity class or object, `onFetch` hook, mandatory fields | `fetchAs()` only fills properties |
| JSON and DateTime columns | delivers strings |
| generated columns, auto increment key, `stripTags`, `NULL` on insert | writes everything given |
| **cache** of entries by primary key | bypasses it |

This leads to:

1. **Missing expressiveness on tables:** condition maps can not express `OR` groups or nested
   conditions; table classes have no way to build them.
2. **Inconsistent results:** the same row is an `OrderEntity` with decoded JSON via `$orders->get()`,
   but a `stdClass` with JSON strings via OSQL.
3. **Inconsistent writes:** OSQL writes generated columns, does not strip tags and writes `NULL` on insert.
4. **Stale cache:** an OSQL `update()` or `delete()` on a cached table is not seen by `$orders->get()`.
5. **`$fields` parameters** of `getAll()` and related methods (planned removal in 0.8) need a replacement
   for selecting some columns with conditions, orders and limits.
6. **No read-only access:** a table can only be handed out completely, with `add()`, `edit()` and
   `remove()` – eg. a table on a read replica (see recipe "Reading from a replica") can write to the replica.

## Goals

- Complex reading (OR groups, joins, aggregates, pages) on tables, delivering entities like `getAll()`.
- Fields, conditions, orders and groupings validated against the declared columns.
- Writes by queries follow the same rules as `add()`, `edit()` and `editByIndices()`, and keep the cache consistent.
- Separation of reading and writing access, also for queries.
- OSQL stays usable without table classes; the dependency goes from PDO to OSQL only.
- Replace the `$fields` parameters, which are removed in 0.8.

## Non-goals

- No ORM: no lazy loading, no identity map, no unit of work.
- No schema reading from the database (`DESCRIBE`) – table classes stay the source of truth.
- No support of other databases than MySQL/MariaDB for the query builder.
- No access control: read-only access in code prevents mistakes, it is no security boundary (see below).

## API surface

### Problem: mixing table methods and query builder verbs

The first draft put `select()`, `insert()`, `update()` and `delete()` directly on `Table`. Evaluated
critically, this causes problems:

1. **Same verbs, other meaning, one layer apart:** `Table\Writer::insert()`, `update()` and `delete()`
   exist already and **execute at once**, returning an ID or a number. `Table::insert()` would return a
   **builder**, doing nothing until `execute()` – a forgotten `execute()` is a silent mistake.
2. **Two ways for the same thing, without a rule:** `add()` vs. `insert()`, `remove()` vs. `delete()`,
   `getAll()` vs. `select()->all()`, `editByIndices()` vs. `update()->where()`. With 45 public methods
   already, teams would have to make their own rules – application code gets inconsistent.
3. **Collisions in subclasses:** application tables extend `Table`. An own method `update()`, `delete()`
   or `select()` with another signature becomes a fatal error with 0.8.
4. **Two writing paths** must follow the same rules forever.

Only reading is a real gap: there is no way to read with `OR` groups, joins or pages by a table today.

### Options

| | Approach | Pro | Contra |
|---|---|---|---|
| A | **One entry:** `$orders->query()` returns an object with the query verbs | one new name on `Table`; builder verbs clearly apart; discoverable | one step more |
| B | **Client takes tables:** `$client->select( $orders )` | `Table` does not grow; good for joins of several tables | a client is needed; not visible on tables; no read-only |
| C | Existing methods take condition objects: `getAll( Group::or( … ) )` | no new verb | conditions only – no joins, aggregates, pages; union types |
| D | Distinct names: `selectQuery()`, `updateQuery()` … | builder obvious | four new methods; problem 2 stays |
| E | Only `select()` on tables, writes by C | no doubling on writes | mass updates with OR groups only by C |

### Decision

- **A, separated by access** – `query()` on reader, writer and table, each offering what its access allows.
- **B as complement** – the client accepts table sources, for code working with the client anyway and
  for joins of several tables.
- **Rule of thumb for documentation:** *table methods for single entries and simple filters – `query()`
  for everything with OR groups, joins, aggregates or pages.*

## Access separation

### Queries by access

| Object | `query()` returns | Verbs | Rules |
|---|---|---|---|
| `Table\Reader` | `ReadQueries` | `select()` | column validation, entities, decoding |
| `Table\Writer` | `WriteQueries` | `insert()`, `update()`, `delete()` | write rules – **no cache**, like the writer methods today |
| `Table` | `TableQueries` (both interfaces) | all four | all rules **plus cache invalidation** |
| `ReadOnlyTable` | `ReadQueries` | `select()` | like `Table`, reading only |

```php
namespace CeusMedia\Database\PDO\Table\Query;

interface ReadQueriesInterface
{
	public function select( ?string $alias = NULL ): TableSelect;
}

interface WriteQueriesInterface
{
	public function insert(): TableInsert;
	public function update(): TableUpdate;
	public function delete(): TableDelete;
}
```

Code that may only read gets a `Table\Reader`, a `ReadOnlyTable` or the type `ReadQueriesInterface` –
a writing method is not reachable, neither at runtime nor for IDE and PHPStan.

Responsibilities stay where they are today: the writer knows no cache, so its write queries do not
invalidate one; the table coordinates reader, writer and cache, so its write queries do – like
`editByIndices()` since 0.7.3.

### Read-only tables

A table combines reading and writing. To hand out reading access only (reports on a replica, a template
layer, code of third parties), there are two poor options today: the whole table (with `add()`, `edit()`,
`remove()`) or its internal reader (without cache and without the convenient methods of the table).

`Table::readOnly()` returns a thin wrapper around the table, which forwards all reading methods and has
no writing methods – same table, same configuration, same cache:

```php
namespace CeusMedia\Database\PDO;

interface ReadableTableInterface        // implemented by Table and ReadOnlyTable
{
	public function get( int|string $id, … ): …;
	public function getAll( array $conditions = [], … ): array;
	public function count( array $conditions = [] ): int;
	public function has( int|string $id ): bool;
	// … all reading methods: getByIndex(), getAllByIndex(), getField(), getDistinct(), …
	public function query(): ReadQueriesInterface;
}

final class ReadOnlyTable implements ReadableTableInterface
{
	public function __construct( private readonly Table $table ) {}

	public function get( int|string $id, … ): …       { return $this->table->get( $id, … ); }
	public function query(): ReadQueriesInterface      { return $this->table->query(); }
	// … forwarding all reading methods – no add(), edit(), remove(), save(), truncate()
}
```

```php
$reports	= ( new OrderTable( $pool->get( 'replica' ) ) )->readOnly();
$reports->getAll( ['status' => 1] );
$reports->query()->select()->fields( 'customerId', 'SUM(total) AS sum' )->groupBy( 'customerId' )->rows();
```

Code expecting reading access type-hints `ReadableTableInterface` – a full table and a read-only table fit.
A wrapper (instead of only the interface) is needed, since an interface alone can be bypassed by
`instanceof Table`.

### Limits of read-only access in code

Read-only access in code prevents writing **by mistake** and documents intent. It is no security
boundary: a connection can always write by itself. A guarantee only comes from **database privileges** –
eg. a database user with `SELECT` only, used for the replica connection.

## Design

### Dependency direction

```
PDO\Table ─────uses──────▶ OSQL (queries, conditions)
     │
     └──implements──▶ OSQL\Source\TableSourceInterface ◀──accepts── OSQL\Client (option B)
```

OSQL defines what it needs from a table as an interface; `PDO\Table`, `Table\Reader` and `Table\Writer`
provide it. OSQL never references `PDO\Table` directly, so it stays usable on its own.

```php
namespace CeusMedia\Database\OSQL\Source;

interface TableSourceInterface
{
	public function getName( bool $prefixed = TRUE ): string;
	/** @return string[] */
	public function getColumns(): array;
	public function getPrimaryKey(): string;
	/** @return string[] */
	public function getIndices(): array;
	public function getRowCodec(): RowCodecInterface;       // decoding on read, encoding on write
	public function getConnection(): PDO;
}
```

The cache is no part of the source: it is handled by the table queries of `Table` only (see above).

### Shared row rules

Rules that exist today inside `Table\Reader` and `Table\Writer` are moved into shared classes, so that
table methods and queries use the same code instead of a copy:

| Class (new) | Taken from | Contains |
|---|---|---|
| `PDO\Table\ColumnGuard` | `Table\Abstraction` (`secureField()`, `secureReference()`, `getFieldAliases()`, function whitelist) | validation of fields, aliases, references against declared columns |
| `PDO\Table\RowDecoder` | `Table\Reader` (`decodeJsonColumns()`, `decodeDateTimeColumns()`, fetch into class/clone, `onFetch`, mandatory fields) | turning a fetched row into the result of the table |
| `PDO\Table\RowEncoder` | `Table\Writer` (`insert()`, `update()`) | skipping generated columns and auto increment key, `NULL` on insert, `stripTags`, encoding JSON and DateTime |

`Table\Reader` and `Table\Writer` delegate to these classes, so behavior of existing table methods does
not change (covered by the existing tests).

## Phases

### Phase 1 – Reading queries and read-only tables

```php
$open	= $orders->query()->select()                // FROM `shop_orders` AS `orders`
	->where( 'status', [0, 1] )
	->or( 'total', 1000, '>' )
	->order( 'createdAt', 'DESC' )
	->page( 2, 20 )
	->all();                                        // OrderEntity[] – JSON/DateTime decoded, onFetch called

$total	= $orders->query()->select()->where( 'customerId', 12 )->count();
$ids	= $orders->query()->select()->fields( 'orderId' )->where( 'status', 0 )->column();
```

- `query()` on `Table\Reader`, `Table` (and `ReadOnlyTable`), `select( ?string $alias = NULL )` returns
  `TableSelect`, a subclass of `OSQL\Query\Select` bound to the table source (see
  [How a query gets its table](#how-a-query-gets-its-table)). Alias of the table: the name without
  prefix by default, so queries read the same with any prefix; an own alias is only needed for self joins.
- **Seen from the table:** columns without qualification are columns of the table itself (`'username'`
  becomes `` `users`.`username` ``); only columns of joined tables are qualified by their alias (`'ug.groupId'`).
- **Column validation:** fields, conditions, orders and groupings must be declared columns of the table
  or of a joined table (or aliases of selected fields, or whitelisted functions) – otherwise
  `DomainException`, like table methods since 0.7.3. Unknown aliases raise a `DomainException`, too.
- **Joins of tables:** `join( $table, $alias, ?$keyLeft, ?$keyRight )` accepts table objects
  (`TableSourceInterface`); they are prefixed and their columns validated. Without keys, the join
  condition is derived from the **own primary key**, if it is a declared **index** of the joined table
  (a foreign key, so to speak): `users.userId = ug.userId`. Otherwise a `DomainException` asks for
  explicit keys. Names and OSQL tables stay possible, without validation of their columns.
  See [Derived joins](#derived-joins) for the rules.
- **Result shape by method, not by fields:** see [Result methods and types](#result-methods-and-types) –
  every method has a fixed return type; selected fields and joins never change it.
- `whereMap( array $conditions )` accepts the compact condition syntax of table methods
  (`['status' => 0, 'total' => '>= 20']`), so maps and builder can be combined.
- Table focus (`focusIndex()` etc.) does not apply to queries.
- **Replacement of `$fields`:** `getAll( $conditions, $orders, $limits, ['orderId', 'total'] )` becomes
  `query()->select()->fields( 'orderId', 'total' )->whereMap( $conditions )->rows()`; the `$fields`
  parameters are removed.
- `Table::readOnly()`, `ReadOnlyTable`, `ReadableTableInterface`.
- Recipe "Reading from a replica" uses `readOnly()`.

Example – usernames of users in group 1 or 2, linked by table `user_groups` (m:n):

```php
$usernames	= $users->query()->select()
	->distinct()                                    // users in both groups only once
	->fields( 'username' )                          // own column
	->join( $userGroups, 'ug' )                     // derived: users.userId = ug.userId
	->where( 'ug.groupId', [1, 2] )                 // column of joined table, validated by UserGroupTable
	->order( 'username' )
	->column();                                     // ['ann', 'bob', 'dan']
```

```sql
SELECT DISTINCT `users`.`username` FROM `app_users` AS `users`
JOIN `app_user_groups` AS `ug` ON `users`.`userId` = `ug`.`userId`
WHERE `ug`.`groupId` IN (?, ?) ORDER BY `users`.`username` ASC
```

#### Result methods and types

If the result shape depended on selected fields or joins, `all()` would return `array|object|Entity` –
the same problem as the `$fields` parameters of `getAll()`, which are removed in 0.8 for that reason.
So, like the field methods taken from `BetterTable` in 0.7.2, **every method has a fixed return type**:

| Method | Returns | Selected columns |
|---|---|---|
| `all()`, `first()` | **rows of the table** (`TRow`): what the table class configures as row – arrays, `stdClass` or entities (see below) – through the `RowDecoder` (JSON/DateTime, `onFetch`, mandatory fields) | always all columns of the base table (`users`.`*`); `fields()` is not allowed and raises a `LogicException` |
| `rows()`, `firstRow()` | plain rows – arrays or `stdClass`, never entities (see open question 9) – JSON/DateTime columns of the base table decoded | `fields()` as given – also columns of joined tables and aggregates |
| `column()`, `value()` | list of values, single value (or `NULL`) | first field |
| `count()`, `exists()` | `int`, `bool` | – |

- With joins, `all()` selects `` `users`.* ``, not `*` – otherwise columns of the same name in other
  tables (eg. `userId`) would overwrite those of the base table. Joins only filter then.
- Reduced rows (some columns of the base table) are no special case any more: they are `rows()`.
- The row type of `all()` depends on the **table class** only, not on the query – so it can be expressed
  by generics, which is the point of this design.

**Row type `TRow`.** The row of a table is not always an entity – it follows fetch mode and entity
settings of the table class:

| Configuration of the table | `all()` returns |
|---|---|
| `FETCH_ASSOC` | `list<array<string,mixed>>` |
| `FETCH_OBJ` (default) | `list<stdClass>` |
| `FETCH_CLASS` and `$fetchEntityClass` | `list<UserEntity>` |
| `FETCH_INTO` and `$fetchEntityObject` | `list<UserEntity>` (filled clones) |

The table class declares its row type; without declaration, it is `array<string,mixed>|object`, as today
(template default, supported by PHPStan 2):

```php
/** @template TRow = array<string,mixed>|object */
abstract class Table { … }

/** @extends Table<UserEntity> */             class UserTable  extends Table { … $fetchEntityClass … }
/** @extends Table<array<string,mixed>> */    class LogTable   extends Table { … FETCH_ASSOC … }
/** @extends Table<stdClass> */               class GroupTable extends Table { … FETCH_OBJ … }

$users->query()->select()->all();       // list<UserEntity>
$users->query()->select()->first();     // ?UserEntity
$users->query()->select()->rows();      // list<array<string,mixed>|stdClass>
$users->query()->select()->column();    // list<mixed>
```

`Table`, `ReadOnlyTable`, `TableQueries` and `TableSelect` are generic (`@template TRow`), and so are
`get()` and `getAll()` of the table itself.

**Row type per query.** A query may need another row type than the table's default – with a type of its
own, without changing the table:

```php
$users->query()->select()->all();                              // list<UserEntity>
$users->query()->select()->asArrays()->all();                  // list<array<string,mixed>>
$users->query()->select()->asObjects()->all();                 // list<stdClass>
$users->query()->select()->fetchAs( UserDto::class )->all();   // list<UserDto>
```

```php
/** @return TableSelect<array<string,mixed>> */
public function asArrays(): TableSelect;

/** @return TableSelect<stdClass> */
public function asObjects(): TableSelect;

/**
 *	@template T of object
 *	@param		class-string<T>		$className
 *	@return		TableSelect<T>
 */
public function fetchAs( string $className ): TableSelect;
```

JSON/DateTime decoding applies to all row types; `onFetch` and mandatory fields belong to the entity
class of the table and apply to its entities only.

**Changing the row type at runtime.** `setFetchMode()`, `setFetchEntityClass()` and `setFetchEntityObject()`
change the row type of an existing table object – which no static type can follow:

```php
$users->setFetchMode( PDO::FETCH_ASSOC );
$users->query()->select()->all();       // PHPStan: list<UserEntity> – actually: arrays
```

This concerns `get()` and `getAll()` today, too. Options:

| | Solution | Consequence |
|---|---|---|
| a | keep the setters, document: "changes the row type, not followed by static analysis" | no break, types may lie |
| b | choose the row type **per query** (`asArrays()`, `asObjects()`, `fetchAs()`) with a type of its own | type safe, table unchanged |
| c | deprecate the setters, row type set by the table class only | clean, breaks code switching at runtime |

Decision for 0.8: **b, plus a** for the time of transition – the table class sets the default, a query
states exceptions. **c** may follow in a later version, once code has moved to per-query row types.

Examples over link table `user_groups`:

```php
$members	= $users->query()->select()           // list<UserEntity>
	->distinct()                                // users in both groups only once
	->join( $userGroups, 'ug' )
	->join( $groups, 'g' )
	->where( 'g.title', ['Admins', 'Editors'] )
	->order( 'username' )
	->all();

$report		= $users->query()->select()           // list<object{username, groups}>
	->fields( 'username', 'COUNT(g.groupId) AS groups' )
	->join( $userGroups, 'ug' )
	->join( $groups, 'g' )
	->groupBy( 'username' )
	->rows();
```

```sql
SELECT DISTINCT `users`.* FROM `app_users` AS `users`
JOIN `app_user_groups` AS `ug` ON `users`.`userId` = `ug`.`userId`
JOIN `app_groups` AS `g` ON `ug`.`groupId` = `g`.`groupId`
WHERE `g`.`title` IN (?, ?) ORDER BY `users`.`username` ASC
```

With `DISTINCT`, MySQL refuses orders by columns not selected – which concerns orders by columns of
joined tables in `all()` only. For large tables, `DISTINCT` over all columns is slower than a filter by
`EXISTS`; this may be added later as condition type, if needed.

#### How a query gets its table

The table creates the query and hands itself over as source – there is no lookup or registry:

1. `Table` (and `Table\Reader`) implement `TableSourceInterface`; `query()` returns `new TableQueries( $this )`.
2. `TableQueries::select()` creates a client on the connection of the table and returns
   `new TableSelect( $client, $this->table )`.
3. `TableSelect` keeps the base table and a map of aliases to sources, starting with the base table
   under its name without prefix. `join()` adds joined tables to this map.

```php
class TableQueries implements ReadQueriesInterface, WriteQueriesInterface
{
	public function __construct( private readonly TableSourceInterface $table ) {}

	public function select( ?string $alias = NULL ): TableSelect
	{
		return new TableSelect( new Client( $this->table->getConnection() ), $this->table, $alias );
	}
}

class TableSelect extends Select
{
	/** @var array<string,TableSourceInterface> $sources Alias => table, base table first */
	protected array $sources	= [];

	public function __construct( Client $client, protected readonly TableSourceInterface $base, ?string $alias = NULL )
	{
		parent::__construct( $client );
		$alias	??= $base->getName( FALSE );
		$this->sources[$alias]	= $base;                                   // 'users' => UserTable
		$this->from( new Table( $base->getName(), $alias ) );              // FROM `app_users` AS `users`
	}

	public function join( TableSourceInterface|Table|string $table, string $alias, ?string $keyLeft = NULL, ?string $keyRight = NULL ): static
	{
		if( $table instanceof TableSourceInterface ){
			$this->sources[$alias]	= $table;                              // 'ug' => UserGroupTable
			if( NULL === $keyLeft )
				[$keyLeft, $keyRight]	= $this->deriveJoinKeys( $table, $alias );
			$table	= new Table( $table->getName(), $alias );              // `app_user_groups` AS `ug`
		}
		return parent::join( $table, $this->resolveColumn( $keyLeft ), $this->resolveColumn( (string) $keyRight ) );
	}

	/** Phase 1: own primary key as index of the joined table: users.userId = ug.userId */
	protected function deriveJoinKeys( TableSourceInterface $table, string $alias ): array
	{
		$primaryKey	= $this->base->getPrimaryKey();
		if( !in_array( $primaryKey, $table->getIndices(), TRUE ) )
			throw new DomainException( 'Cannot derive join: "'.$primaryKey.'" is no index of "'.$table->getName( FALSE ).'" - give keys' );
		return [$primaryKey, $alias.'.'.$primaryKey];
	}

	/** 'username' → 'users.username'; 'ug.groupId' → validated against UserGroupTable */
	protected function resolveColumn( string $column ): string
	{
		[$alias, $name]	= str_contains( $column, '.' )
			? explode( '.', $column, 2 )
			: [array_key_first( $this->sources ), $column];                // unqualified: base table
		$source	= $this->sources[$alias] ?? throw new DomainException( 'Unknown table alias "'.$alias.'"' );
		if( !in_array( $name, $source->getColumns(), TRUE ) )
			throw new DomainException( 'Column "'.$name.'" is not a column of table "'.$source->getName( FALSE ).'"' );
		return $alias.'.'.$name;
	}
}
```

`fields()`, `where()`, `having()`, `order()` and `groupBy()` pass every column through `resolveColumn()`
before handing it to `Select`; functions (`COUNT(ug.groupId)`) and aliases of selected fields are
recognized first, by the logic of `ColumnGuard`. Joins of names or OSQL tables (without source) are
not validated – the alias map only knows table sources.

The query holds a **reference** to the table object, no copy of its settings: entity class and fetch
mode are read on execution, like by table methods today.

#### Derived joins

A join of a table source without keys is derived from **primary keys and declared indices**: a column
of the same name as the primary key of one table, declared as index in the other table, is taken as
foreign key. Indices instead of columns, since a column of the same name is a weak signal – with
`id` as primary key in all tables, a rule by columns would link `a.id = b.id`; the primary key is no
part of `$indices`, so the rule by indices does not.

Candidates, when joining table `N` (alias `n`) to a query with tables `S` (alias `s`):

| Direction | Condition | Join | Phase |
|---|---|---|---|
| base → new | primary key of base table is an index of `N` | `base.pk = n.pk` | 1 |
| new → base | primary key of `N` is an index of the base table | `base.pk(N) = n.pk` | 5 |
| any joined → new | primary key of a joined table `S` is an index of `N` | `s.pk = n.pk` | 5 |
| new → any joined | primary key of `N` is an index of a joined table `S` | `s.pk(N) = n.pk` | 5 |

- **Exactly one candidate** is used.
- **No candidate:** `DomainException` – give keys (or declare the foreign key column as index).
- **Several candidates:** `DomainException` listing them – give keys. No guessing by order of tables.

Requirements and consequences:

- The rule relies on the naming convention "foreign key column = name of primary key" (`userId`), as
  used in CeusMedia tables. Tables with primary key `id` get no derived joins – explicit keys are
  needed, which is better than a wrong join.
- Foreign key columns must be declared in `$indices`. This also allows them as filters of
  `getAllByIndex()`, `editByIndices()` etc. – mostly intended anyway.
- Composite primary keys are not supported by table classes; link tables need a primary key of their
  own (eg. `userGroupId`) or explicit keys.

Example – usernames of users in groups "Admins" or "Editors", over link table `user_groups`:

```php
$usernames	= $users->query()->select()
	->distinct()
	->fields( 'username' )
	->join( $userGroups, 'ug' )                     // phase 1: users.userId is index of UserGroupTable
	->join( $groups, 'g' )                          // phase 5: groups.groupId is index of joined UserGroupTable
	->where( 'g.title', ['Admins', 'Editors'] )
	->order( 'username' )
	->column();
// until phase 5: ->join( $groups, 'g', 'ug.groupId', 'g.groupId' )
```

```sql
SELECT DISTINCT `users`.`username` FROM `app_users` AS `users`
JOIN `app_user_groups` AS `ug` ON `users`.`userId` = `ug`.`userId`
JOIN `app_groups` AS `g` ON `ug`.`groupId` = `g`.`groupId`
WHERE `g`.`title` IN (?, ?) ORDER BY `users`.`username` ASC
```

### Phase 2 – Writing queries

```php
$orders->query()->update()->set( 'status', 2 )->where( 'customerId', 12 )->and( 'status', 1 )->execute();
$orders->query()->delete()->where( 'createdAt', '2020-01-01', '<' )->execute();
$orders->query()->insert()->addRow( $order1 )->addRow( $order2 )->execute();
```

- `query()` on `Table\Writer` and `Table`, with `insert()`, `update()`, `delete()` returning
  `TableInsert`, `TableUpdate`, `TableDelete`.
- Values go through the `RowEncoder`: generated columns and an auto increment primary key are skipped,
  `NULL` is left out on insert, tags are stripped (unless `stripTags( FALSE )`), JSON/DateTime are
  encoded. Columns must be declared.
- **Cache (table queries only):** if caching, update and delete read the primary keys of affected rows
  first (same conditions, `SELECT pk`) and remove them from the cache after execution – within a
  transaction, so reading IDs and changing rows see the same rows. Inserts do not touch the cache.

### Phase 3 – Client with table sources (option B)

```php
$rows	= $client->select( $orders, 'o' )
	->fields( 'o.orderId', 'o.total', 'c.name' )
	->join( $customers, 'c', 'o.customerId', 'c.customerId' )
	->rows();
```

- `Client::select()`, `insert()`, `update()`, `delete()` accept a `TableSourceInterface` besides names:
  `$client->select( $orders, 'o' )` returns the same `TableSelect` as `$orders->query()->select( 'o' )` –
  prefixed names and column validation for all tables of the query, also joined ones.
- Writes by the client use the write rules of the source, but **no cache** (the client knows no table);
  this is documented: for cached tables, write by `$table->query()`.

### Phase 4 – Table methods on the builder

- Table methods (`getAll()`, `getAllByIndices()`, `count()`, `editByIndices()`, `removeByIndices()` …)
  are implemented by the queries internally – one implementation of reading and writing rules, table
  methods become convenient shortcuts.
- Behavior and signatures of table methods stay (besides the removed `$fields`); covered by the
  existing tests.

### Phase 5 – optional: relations and more derived joins

- **More derived joins:** phase 1 derives a join only from the primary key of the base table. Phase 5
  applies the rules of [Derived joins](#derived-joins) to **all tables already in the query** and
  **both directions** – eg. `orders` to `customers` (`orders.customerId = c.customerId`) and a second
  join over a link table (`ug.groupId = g.groupId`).
- **Declared relations** (only if derivation is not enough):
  `protected array $relations = ['customer' => [CustomerTable::class, 'customerId']];` and `->with( 'customer' )`.

## Open questions

1. **Name of the entry:** `query()` may be confused with `Connection::query()`, which executes SQL.
   Alternatives: `queries()`, `builder()`. Proposed: `query()`, documented clearly.
2. ~~Default alias~~ – decided: name without prefix; columns without qualification belong to the table itself.
3. **Condition maps in builder:** is `whereMap()` worth it, or should the compact value syntax
   (`'>= 20'`) stay a table-method feature? Proposed: yes, to replace `$fields` easily.
4. ~~Partial rows~~ – decided: result shape by method; reduced rows are `rows()`, `all()` always
   delivers complete rows of the table.
5. **Cache on update/delete with limit or order:** read IDs with the same limit/order (exact, one query
   more) or clear the whole table cache? Proposed: read IDs.
6. **Read-only wrapper:** forwarding by hand (explicit, typed) or by a trait/generator? Proposed: by
   hand, the list of reading methods is stable.
7. **Relations (phase 5):** derive only, or declare? Proposed: derive first, declare only if needed.
8. **`all()` of `Select` and `TableSelect`:** OSQL's `Select::all()` returns plain rows and accepts
   `fields()`; `TableSelect::all()` returns rows of the table and refuses `fields()` – a subclass being
   stricter than its parent. Proposed: add `rows()`/`firstRow()` to `Select` (plain rows, as `all()` there),
   document `all()` as "rows of the source" – plain rows for OSQL tables, table rows for table sources –
   and recommend `rows()` for plain rows everywhere.
9. **Form of `rows()`:** arrays if the row type of the table is an array, `stdClass` otherwise (never
   entities) – close to `all()`, but its type depends on the table (`list<array<string,mixed>|stdClass>`).
   Alternative: always `array<string,mixed>` – one fixed type, simple for PHPStan, but unlike `all()` for
   tables fetching objects. Undecided.

## Compatibility

- Phases 1–3 and 5 are additive: existing table methods and OSQL queries keep their behavior.
- One new public name on `Table` (`query()`) and `readOnly()` – collisions with methods of application
  subclasses are possible, but unlikely; to be checked in own projects before release.
- Moving rules into `ColumnGuard`, `RowDecoder` and `RowEncoder` (and phase 4) changes protected methods
  of `Table\Abstraction`, `Table\Reader` and `Table\Writer` – relevant only for subclasses overriding them.
- Removal of the `$fields` parameters (planned for 0.8) is done in phase 1, since `select()->fields()`
  replaces them.
- Generic row types are additive for code without declaration (default `array<string,mixed>|object`).
  Setters of the row type stay, but are documented as not followed by static analysis; a deprecation
  may follow later (option c).

## Tests

- Unit tests of `ColumnGuard`, `RowDecoder`, `RowEncoder` (moved from existing reader/writer tests).
- Query tests against MySQL: prefix and alias, unqualified columns of the base table, joins of table
  sources (derived and explicit keys, no and several candidates, `id` as primary key, unknown alias, column of wrong table), validation, result methods (`all()` with complete rows also with joins, `fields()` on `all()` raising, `rows()`, `column()`, `value()`), PHPStan checks of the generic return types (declared `TRow`, default, `asArrays()`/`asObjects()`/`fetchAs()`),
  decoding, `onFetch`, write rules, cache invalidation of table queries and none of writer queries.
- Access tests: reader and read-only table offer no writing (`ReadQueriesInterface` only), writer
  offers no reading queries; `ReadOnlyTable` forwards all reading methods (checked by reflection
  against `ReadableTableInterface`).
- The existing table tests must pass unchanged after the refactoring and after phase 4.
